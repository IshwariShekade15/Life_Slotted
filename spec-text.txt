SLOTTED
Auto-schedule your life around everything. No planning required.
AI Agent Build Specification 227 v1.1 267 Includes Meeting Blocks
Most productivity apps make you do the planning. You still have to decide what goes where, dragblocks around when life happens, and restart when you fall behind. Slotted removes that entirelayer. You dump what you need to do 227 with a deadline, a rough duration, and how often itrepeats 227 and the app builds your schedule automatically. When something goes sideways (andit will), Slotted rebalances without you lifting a finger. It never shows you a streak you broke. Itnever pretends you have more time than you do. It just keeps you moving.

177 People with ADHD who freeze at the planningstage
177 Students managing assignments, exams, andsocial life
177 Anyone who over-commits and discovers it too late
177 People who fall off a habit and give up because thestreak reset
177 Professionals juggling recurring and one-off work
177 People who want honesty 227 'you won't finish thisby Friday' 227 not false comfort
177 Anyone tired of spending 30 min planning a 2 hrworkday

The Core Problem Being Solved
177   Planning fatigue: for ADHD users especially, the act of planning is as exhausting as the work itself.Slotted makes the plan for you.
177   False scheduling: most apps let you add infinite tasks without telling you there's no time for them.Slotted shows your real remaining capacity live.
177   Rigidity on failure: when one task runs late or gets skipped, every other app breaks 227 youmanually drag everything. Slotted auto-rebalances.
177   Shame mechanics in habit apps: streak counters that reset to zero punish ADHD users who falloff. Slotted uses rolling % instead 227 one missed day barely moves the needle.

COMPLETE FEATURE LIST
CORE SCHEDULING ENGINE
177   Brain-dump task entry: add a task with just a title and duration 227 every other field is optional. Nofriction, no long forms up front.
177   Auto-scheduling: the algorithm places every task and habit into the user's available time windowsautomatically. Zero manual time-blocking.
177   Priority-based sorting: each task has a user-set priority (High / Medium / Low) that controls wherethe scheduler places it relative to others.
177   Task decay / urgency creep: a task's effective scheduling priority rises automatically as its deadlineapproaches 227 a 'Low' task due tomorrow will outrank a 'High' task due next month. Recomputed onevery schedule run.
177   Deadline awareness: every task can have an optional deadline. The scheduler ensures deadlinetasks are slotted before their due date or flags them if they won't fit.
177   Divisible tasks: long tasks (e.g. a 3hr project) can be marked splittable. The scheduler breaks theminto chunks (minimum chunk size set by user) and slots each chunk into separate available windows.
177   Recurring tasks and habits: tasks can recur daily, weekdays only, on custom selected days, or Ntimes per week. The scheduler handles recurrence automatically.
177   Availability windows: users define when they're free each day (e.g. Mon226Fri 9am22610pm). Thescheduler only places tasks inside these windows 227 never outside.
177   At-risk flagging: if a task cannot be scheduled before its deadline given current capacity, it'sflagged 'at risk' and surfaced prominently 227 not silently dropped.
AUTO-REBALANCING (KEY DIFFERENTIATOR)
177   Instant rebalancing on skip: if a task block is skipped, the scheduler immediately re-slots it into thenext viable opening 227 no manual dragging.
177   Instant rebalancing on completion: if a task finishes early, remaining capacity is freed and thenext pending task is pulled forward.
177   Cascade on edit: editing a task's duration, deadline, or priority triggers a full reschedule soeverything else adjusts accordingly.
177   'Redo my day' button: one-tap full rebalance from Today view. Useful when the day goescompletely sideways.
177   Moved indicator: blocks that were auto-moved show a 'rescheduled' badge so the user knows whatshifted and why.
177   Background cron rebalance: every 15 minutes, the backend checks for blocks whose time passedwithout completion and automatically re-slots them.
CAPACITY FORECASTING (KEY DIFFERENTIATOR)
177   Live 'X hours free this week' display: shown on the Dump screen and Week view, updated in realtime as tasks are added.
177   Overcommitment warning: if adding a new task would push total scheduled time beyond availablecapacity, an inline orange warning appears 227 user can still save, but they see it clearly.
177   Per-day capacity awareness: the scheduler knows how much free time exists on each individualday, not just the week total.
HABIT TRACKING (KEY DIFFERENTIATOR)
177   Streak-free tracking: habits are tracked as a rolling 14-day and 30-day completion percentage. Nostreak counter. Ever. One missed day barely moves the needle instead of resetting to zero.
177   Calendar heatmap: each habit has a last-30-days heatmap (green = done, grey = missed) so userscan see patterns without judgment.
177   Colour-coded health bar: green if % > 70, amber if 4022670, red if < 40. Calm and informative, notpunitive.
177   Habit blocks on schedule: habits appear on Today view and Week view like regular tasks 227 tap tomark complete or missed.

MEETING BLOCKS (FIXED TIME COMMITMENTS)
177   One-off meeting: user adds a meeting with a title, date, start time, and end time. That time windowis immediately blocked off 227 the scheduler will never place a task there.
177   Recurring meeting: user can set a meeting to repeat daily or on specific days of the week (e.g.every Monday and Wednesday). They also set an end date 227 the recurring meeting stops generatingblocks after that date.
177   Meeting recurrence options: One-time only / Every day / Custom days (weekday checkboxes) /Every weekday (Mon226Fri). Plus an optional end date for all recurring types.

SYSTEM DESIGN PRINCIPLES 227 BUILD TO THESE
API DESIGN
177   RESTful, resource-oriented: /tasks, /schedule, /habits, /availability 227 no RPC-style endpoints.
177   Single responsibility: each endpoint does one thing. POST /tasks creates a task. The schedulerruns as a side effect internally, not a separate manual API call the frontend has to make.
177   Optimistic UI: frontend updates the local state immediately on user action, then confirms with theserver. If the server fails, roll back with an error message. Never make the user wait for a spinnerbefore seeing their task appear.
177   Idempotent scheduler: running the scheduler twice on the same data produces the same result. Noduplicate blocks. Use upsert, not insert.
177   JWT auth only: never accept user_id as a body or query parameter. Always extract it from thevalidated Supabase JWT in the Authorization header.
177   RLS on every Supabase table: users can only read/write their own rows. This is enforced at thedatabase level, not just the API level.
SCHEDULER DESIGN
177   Stateless per run: the scheduler takes inputs (tasks, availability, current time) and returnsscheduled blocks. It does not store intermediate state or depend on the previous run's output.
177   Deterministic: same inputs always produce the same output. This makes it testable anddebuggable.
177   Separation from API: scheduler.py is a pure Python module with no FastAPI imports. The API layercalls it; the scheduler doesn't know about HTTP.
177   Graceful degradation: if a task cannot be scheduled, the app tells the user clearly (at-risk flag) andcontinues scheduling everything else. Never crash or return an empty schedule because one task didn'tfit.
177   Write unit tests for the scheduler before building the API. Test: priority decay formula, slot-fittingwith exact minute boundaries, chunk splitting, at-risk detection, rebalancing after a skip.
FRONTEND ARCHITECTURE
177   Component hierarchy: App 256 Layout (BottomNav) 256 Screen (Today / Week / Dump / Backlog /Habits). Screens are independent route-level components.
177   Global state: use React Context or Zustand for: current user, schedule data, capacity stats, loadingstates. Do not prop-drill these.
177   Data fetching: use React Query (TanStack Query) for all API calls. It handles caching, refetching onfocus, and loading/error states cleanly.
177   After any mutation (complete/skip/add/delete): invalidate the /schedule query so Today andWeek views refetch automatically.
177   CSS variables for theming: all colours defined as --color-* variables on :root. Dark mode overridesin @media (prefers-color-scheme: dark). Never hardcode hex values in component files.
177   No inline styles: all styling via Tailwind utility classes. For complex one-off styles, use a CSSmodule.
ERROR HANDLING 227 NON-NEGOTIABLE
177   Every API call has a try/catch. No unhandled promise rejections.
177   Network errors: show an inline 'Something went wrong 227 tap to retry' message, not a blank screen.
177   Validation errors: returned from FastAPI as 422 with field-level detail. Frontend maps these toinline field errors, not a generic toast.
177   Scheduler failures: if the scheduler errors (e.g. corrupted availability data), return the user's existingschedule unchanged and log the error. Never return an empty schedule.
177   Auth expiry: if JWT expires mid-session, redirect to login with a 'Session expired 227 please log inagain' message. Do not silently fail.

SCHEDULING ALGORITHM
EXECUTION STEPS (RUN ON EVERY TRIGGER)
1.   Fetch all pending/scheduled tasks for the user from Supabase.
2.   Fetch user availability windows for the target date range (today + 7 days).
3.   For each task: compute effective_priority_score. Base: High=100, Medium=60, Low=30. Deadlineboost: <24h +80 / <48h +50 / <72h +30 / <168h +10. No deadline = base score only.
4.   Sort tasks: descending by effective_priority_score. Tiebreaker: soonest deadline. Habits on theirdesignated days get priority over one-off tasks in the same window.
5.   Build a per-day free-slot map from availability windows minus already-placed scheduled_blocksAND minus all meeting_blocks for that day. Meeting blocks are hard constraints 227 treatedidentically to unavailable time. A task is never placed in a meeting slot under any circumstance.
6.   For each task (sorted): find the earliest free slot that fits the full duration before the deadline.Place it. Remove that slot from the free-slot map.
7.   If divisible and no single slot fits: split into chunks 263 min_block_minutes. Place each chunkgreedily.
8.   If no valid placement exists before deadline: mark task 'at_risk'. Do not crash. Continue withremaining tasks.
9.   Upsert all resulting scheduled_blocks (delete old pending blocks for the user, insert new ones).Never duplicate.
10.   Return: list of scheduled_blocks for the week + meeting_blocks for the week +{total_available_minutes, total_meeting_minutes, total_scheduled_minutes, free_minutes} capacitystats. free_minutes = total_available - total_meeting - total_scheduled.
Write and unit-test scheduler.py BEFORE connecting it to the API. Test with mock data. It must bedeterministic and stateless.
